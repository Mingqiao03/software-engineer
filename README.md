## 硬性要求（工程型，容易忽略的几条）

**复杂度**：至少满足下列 3 项 —— 多个目标不同的利益相关者 / 明显需求冲突或价值权衡 /
复杂业务规则或领域知识 / 涉及多系统或多组织接口 / 有安全·隐私·可靠性·实时性·可用性要求 /
需求不确定且持续变化 / 涉及人机协同·智能推荐·自动决策或生成式 AI / 失效有业务社会安全影响 /
需在成本性能质量进度间权衡。
> 单纯信息录入、静态展示、普通课程管理、简单电商页面通常**不算**满足复杂度。

**必须两个原型**，且是两个**不同的方案/设计假设**（不同业务流程、人机职责、交互方式、
系统边界、自动化程度、隐私性能权衡、规则 vs AI、集中 vs 分布……）。
> 不算独立原型：原型 2 只是修 bug / 加页面 / 原型 1 的视觉美化 / 需求假设与核心流程完全相同。
> ⚠️ 一票否决式上限：**只有一个有效原型 → 最高 69 分**。

**需求获取至少两种方法**（访谈/问卷/观察/工作坊/文档法规/日志数据/场景/原型反馈/竞品）。
> 接触不到真实利益相关者时必须写明限制，并用领域专家/公开资料/模拟角色/历史数据补充验证；
> **不得虚构访谈对象与结果**（伪造访谈 = 不予通过）。
> ⚠️ **没有真实需求获取或替代证据 → 最高 74 分**。

**评估不能只问"喜不喜欢"**，要有任务、指标、基线、比较对象。
> ⚠️ **没有基于需求的原型评估 → 最高 74 分**。

**追踪矩阵**：业务目标/干系人需要 → 系统需求 → 原型特性/设计决策 → 测试与评估证据。
须区分：已满足 / 部分满足 / 未满足 / 尚未验证 / 原型引出的新增需求 / 原型间权衡。

**生成式 AI 使用说明**（报告必备章节）：用了什么工具、用在哪些环节、典型提示、
人工核验修改方式、已知风险局限。允许用 AI，但必须核实事实/文献/需求/代码，
**不得把 AI 模拟结果冒充真实访谈或用户反馈**。未提交说明会在规范维度扣分。

**关键发现 1**：访谈推翻了建议书的初始假设——**Slurm 已是实验室基础设施**。
项目边界应改为"Slurm 之上的申请、解释、通知与协同层"，而非重造调度器。

**关键发现 2**（INT-04）：**任何额外填写都会被规避**。
"维护表格的时间比跑实验的时间还长"——已有登记表因无人填写而停用。
这不是用户不守规则，而是"登记成本 > 收益"时规则必然失效。
→ 这条直接约束原型 A 的设计：**必须自动采集，不能靠用户填报**，否则会重演旧表格的结局。

**关键发现 3**：**痛点只在资源争抢期出现**（投稿/项目节点），平时资源不紧张。
系统不能按"长期排队"设计。同时 H1 已被两次修订，演化链本身就是期末 §15 的素材。

**关键发现 4**（竞品分析，2026-10-21）：**Slurm 已有排队、fair-share、QOS/配额、预留、ETA、邮件、核算、GPU 记账**——
重写调度器是重复建设。真正缺的是**治理层**：申请单/审批状态机、预约日历、排序解释、主动通知。
Slurm 的 reservation 只是"管理员创建的时间窗"，官方模型里**没有审批实体**。

**关键发现 5**（推论，待证实）：实验室可能有**两本账**——经 Slurm 提交的作业有 `sacct` 记录，
SSH 直连的交互式使用（INT-04 的路径）对 Slurm 完全不可见。
若属实，核心难点不是"更聪明的调度规则"，而是**让不经过 Slurm 的负载变得可见**；
旧登记表失败也正因为要求人手工报告一件系统看不见的事。

> ⚠️ 这条推论**尚未证实**，管理员访谈的第一个问题就该是：**"组里 GPU 全部走 Slurm，还是允许 SSH 直连？"**
> 它的答案决定项目边界，也决定两个原型的差异维度——从"算法不同"改为"**边界与自动化程度不同**"。
