# 方法 2：竞品分析与能力边界（v1.0，2026-10-21）

> **方法定位**：课程允许的获取方法之一。本文回答"**现有工具已经解决了什么、还缺什么**"，
> 用于约束系统边界、验证访谈中"想要的功能是否其实已经存在"。
> **它不能替代用户证据**——竞品分析回答"技术上有什么"，不回答"本实验室的人实际要什么"。

## 一、做法与可核实性

- **检索日期**：2026-10-21
- **材料范围**：官方文档（slurm.schedmd.com、NVIDIA 文档、Open OnDemand 文档）+ 公开仓库 README
- **规则**：只写实际打开并核对过的页面；未核实的标注"未验证"，不据推测补全
- **产出**：能力对照表 + 5 条结论 + 对需求的推论

> 与访谈的关系：访谈里用户提的"看排队""通知""配额"等诉求，**先在这里查有没有现成能力**。
> 已有的不重造，没有的才进入需求。这能避免"用户想要 → 我们就做"的重复建设。

## 二、竞品选择

| 对象 | 为什么选它 | 在本项目中的角色 |
|---|---|---|
| **Slurm** | 实验室正在使用的基础设施（访谈已证实） | 执行层与账本，不是竞品而是**被集成的对象** |
| **nvitop / gpustat / nvidia-smi** | 用户实际用来"看谁在占卡"的工具 | 监控层，回答"现在"，不回答"该给谁" |
| **Open OnDemand** | 高校 HPC 常见门户 | 门户层的参照 |
| **TensorHive / ColdFront / FastReserve** | 三个方向不同的实验室级工具 | 用来判断"自建 vs 拼装"的设计空间 |

> 选择理由不是"知名度"，而是**它们各自代表一种被现有实践验证过的解法**。

## 四、五条结论

**结论 1：Slurm 已经解决了"调度原语"，重写它就是重复建设。**
排队、优先级、fair-share、QOS/配额、预留、时间控制、ETA、邮件通知、核算、GPU 申请与 GPU TRES 记账都已内置 [1][4][7][11][14]。
项目应把 Slurm 当作**执行与账本系统**，通过 `slurmrestd` [26] 或 `sacct` 读取状态。

**结论 2：真正的缺口是治理层，不是调度器。**
Slurm 的 reservation 是"**管理员创建的资源时间窗**"，不是"学生提交申请 → 审批 → 获得时段"的业务流程；
官方文档中没有申请单、审批人、审批状态这类实体 [4]。
这正是访谈里"口头协商、无记录"所填补的空白。

**结论 3：Open OnDemand 补的是门户，不是审批。**
它提供网页入口、作业提交与交互应用；Project Manager 文档只描述 launcher、workflow、项目目录，没有分配审批 [18][19][20]。

**结论 4：现有开源工具各补一块，没有一个拼成闭环。**

| 工具 | 有 | 缺 |
|---|---|---|
| TensorHive [21] | 日历预约、独占 GPU、违规检测告警（Apache-2.0） | README 未提审批；未集成 Slurm |
| ColdFront [22] | 分配申请/审批/到期、Slurm 账户自动化（GPLv3） | 不是 GPU 时段日历 |
| FastReserve [23] | 面向高校实验室、有审核页面 | 仅 7 个 commit，未见许可证文件，未集成 Slurm |

> 这组对照直接支撑一个设计判断：**"自建 vs 拼装"本身就是两个原型可以区分的维度之一**（见第六节）。

**结论 5：监控不等于分配，且账本有盲区。**
nvitop/gpustat 能回答"现在谁在用哪块 GPU"，但不排队、不限额、不做公平 [15][16][17]。
更关键的是：`nvidia-smi` 的 per-process accounting 是**有限的环形缓冲**，不能当配额/公平账本 [17]。
因此，**凡是不经 Slurm 的直连使用，Slurm 的 fair-share 与核算都看不到**。

## 五、一个关键推论：实验室可能有两本账

访谈证据与竞品能力叠加后，出现了一个建议书没有预料到的问题：

- INT-04 描述的路径是 `SSH → nvidia-smi → bash 脚本`，**全程没有出现 Slurm**（INT-04/00:57–02:50）；
- INT-01～03 描述的是 `sbatch` 排队与等待（INT-01/E02、INT-03/E11）。

两条路径**可能同时存在**。如果属实，则：

| | 经 Slurm 提交 | SSH 直连 |
|---|---|---|
| 谁看得见 | 全组（`squeue`） | 只有登上去的人（`nvidia-smi`） |
| 是否记账 | ✅ `sacct` | ❌ |
| 是否受配额/公平约束 | ✅ | ❌ |
| 冲突怎么解决 | 排队 | 私下协调（INT-04/E21） |

**含义**：系统的核心难点不是"设计一套更聪明的调度规则"——那部分 Slurm 已经有了；
而是**让不经过 Slurm 的那部分负载变得可见**。这恰好解释了为什么旧登记表会失败：
它要求人手工报告一件系统看不见的事（INT-04/E19、INT-02/E07）。

> ⚠️ **这是推论，不是已证实的事实。** 访谈中没有直接问"你是否用 Slurm"，也没有核实是否存在
> 完全绕开 Slurm 的节点。需在管理员访谈中用一句话确认：
> **"组里的 GPU 是全部经由 Slurm 提交，还是允许 SSH 直连使用？"**
> 这一问的答案会决定项目边界，是下一次访谈的**首要问题**。

## 六、对系统边界与两个原型的修订

### 6.1 边界修订

| 层 | 归属 | 依据 |
|---|---|---|
| 作业执行、排队、公平份额、配额执行 | **Slurm**（外部系统） | 结论 1 |
| 用量核算 | **Slurm accounting**（外部系统） | 结论 1 |
| 进程级实时监控 | **nvitop/nvidia-smi**（集成） | 结论 5 |
| **申请与审批状态机** | 本项目 | 结论 2 |
| **预约日历与冲突处理** | 本项目 | 表 1 |
| **排序/等待的解释** | 本项目 | ETA 只有一个 reason code [10] |
| **审批、预约、配额的主动通知** | 本项目 | Slurm 只覆盖作业事件 [5] |
| **非 Slurm 路径的可见性** | 本项目（若推论成立） | 结论 5 |

### 6.2 两个原型的差异维度需要调整

建议书设想的差异是"先到先得 vs 配额/优先级调度"。竞品分析表明：

- 如果资源都走 Slurm，**"配额/优先级调度"已经有现成实现**，原型 B 再做一遍，价值会打折；
- 更有区分度的差异维度其实是 **"系统边界与自动化程度"**：

| | 原型 A | 原型 B |
|---|---|---|
| 边界 | 薄层：只做申请、日历、通知，调度完全交给 Slurm | 厚层：自带配额与排序评估，Slurm 只负责执行 |
| 非 Slurm 使用 | 不处理（假设全部走 Slurm） | 通过监控与心跳推断占用，尽量覆盖 |
| 成本 | 低，落地快 | 高，但覆盖盲区 |
| 风险 | 直连用户仍然不可见 | 规则复杂、维护成本高 |

> 这个修订**不推翻建议书**，而是让它更站得住：差异从"算法"移到"边界与自动化程度"，
> 更符合竞品分析给出的真实设计空间，也更容易在评估中做出可观察的差别。
> 是否采纳，等管理员访谈确认"是否存在直连使用"后再定。

## 九、局限与未验证项

必须写进报告，不能删：

1. **竞品分析不是用户证据**。它只能证明"工具有什么"，不能证明"本实验室需要什么"。
2. **"Slurm 不提供审批"是文档事实的推论**，官方没有一句否定声明；也未排查第三方插件生态。
3. **版本边界未全部核实**：只确认 multifactor 在 14.11 存在、`--gpus` 在 19.05 存在、
   Fair Tree 19.05 默认、MIG 21.08；各能力的首次引入版本未验证。**实验室实际版本未知**，需 DOC-01。
4. **TensorHive / ColdFront / FastReserve 只读了公开 README**，未部署试用；维护状态与生产可用性未验证。
5. **"没有工具同时覆盖全部"是抽样判断**，不是系统性综述。
6. **第五节"两本账"是推论**，尚未经管理员确认——**在确认前，不得在报告中写成事实**。
