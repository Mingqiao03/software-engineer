## 1 结论摘要

四次访谈共同表明：实验室已经使用 **Slurm 队列**解决了一部分"抢卡"和空占问题，因此项目**不应重复开发底层调度器**。
真正未被充分解决的是：预计等待与完成时间不清楚、申请信息过少、冲突依赖人际协调、异常或人工操作缺少及时通知、
公平规则难以同时兼顾短任务/长任务/紧急任务，以及**任何需要额外填写的流程都会被规避**。

本轮得到**九项**阶段性结论：

1. **Slurm 是现状基础设施，但可能不是唯一入口。** 四位受访者均通过 Slurm、`nvidia-smi` 或相关命令判断资源状态；
   其中 INT-01/02/03 明确使用 Slurm 队列，**INT-04 只使用 `nvidia-smi` 直连**（见 §3）。
   系统方案应作为 Slurm 之上的申请、解释、通知和协同层。
2. **"看得到队列"不等于"知道要等多久"。** 受访者仍希望知道前方任务数量、预计剩余时间和大致启动时间；
   可接受等待上限因人和场景而异，从约 1 小时到 12 小时不等。
3. **纯手工登记曾失败。** 已有资源使用表因成员不持续填写、维护成本高而停用；另一种按时段预约的表格
   还出现"占了时段但没有实际用卡"的问题。
4. **固定平均配额缺少支持。** 两名受访者明确认为任务规模差异大，简单按人平均 GPU 小时不合适；
   更可接受的是等待时间、任务时长和必要性共同参与排序。
5. **任务能否中断是关键属性。** 调试、验证类任务被认为不宜中断，可重复的批处理任务更容易让出资源。
   直接自动终止任务存在较高风险。
6. **冲突处理主要依赖同伴协商。** 当前缺少明确的审批者和统一证据标准。受访者通常接受"真正紧急"的任务优先，
   但希望说明原因，反对无解释的停任务或插队。
7. **异常通知和责任识别有真实证据。** 存在容器被误停后排查半天的经历；服务器不可用时，用户希望收到明确通知。
8. **（新增）登记成本必须接近零，否则流程必然被绕过。** INT-04 明确表示"维护表格的时间比跑实验的时间还长"，
   并描述了一条完全不经过任何登记与协商的用卡路径。这不是用户不守规则，而是"登记成本 > 收益"时规则自然失效。
   **这条对系统设计是硬约束，不是偏好。**
9. **（新增）痛点只在资源争抢期出现。** INT-04 指出非投稿期"大家不会那么急，队列也没有那么长"。
   系统不能按"长期排队"设计，否则大部分时间处于空转；同时，短任务用户在无争抢时对现状是满意的，
   这说明 H1（状态不透明）**只在争抢场景成立**，不能笼统表述。

**结论边界**：四位受访者均为同一实验室成员，尚未覆盖**正式服务器管理员、老师和低频用户**；
单场访谈约 6–10 分钟，未完整执行原计划的 40–45 分钟问题清单，也未使用公平情景卡。
因此，本报告可作为第一次检查的真实需求获取证据，但不能单独构成最终需求基线。

> 另有一个**由竞品分析引出、尚待管理员确认的推论**：实验室可能存在"两本账"——
> 经 Slurm 提交的作业有 `sacct` 记录，而 SSH 直连的交互式使用对 Slurm 不可见。
> 详见 §3、§9.3。**在确认前不得写成事实。**

## 3 当前工作流程与系统边界

四次访谈反映的现状**不止一条路径**。前 3 场以 Slurm 排队为主，INT-04 则完全不经过 Slurm：

```
                      ┌──────────────── 路径 1（INT-01/02/03）────────────────┐
 规划实验 → 确定卡数 → 提交 Slurm 队列 → 等待/换卡 → 运行 → Slurm 释放 → sacct 有记录
                      └───────────────────────────────────────────────────────┘

                      ┌──────────────── 路径 2（INT-04）───────────────────────┐
 规划实验 → SSH 登录 → nvidia-smi 看占用 → 有空卡即跑 → 结束，不通知任何人 → 无记录
                      └───────────────────────────────────────────────────────┘
```

两条路径的差别不只是操作方式，而是**可观测性与治理能力的差别**：

| | 路径 1：经 Slurm | 路径 2：SSH 直连 |
|---|---|---|
| 谁看得见 | 全组可通过 `squeue` 看到 | 只有登上去执行 `nvidia-smi` 的人 |
| 是否记账 | 有 `sacct` 记录 | 无 |
| 是否受配额/公平约束 | 是 | 否 |
| 冲突解决方式 | 排队 | 私下协调，必要时找管理员 |
| 是否需要额外填写 | 少量或不需 | 无 |

**关键判断（推论，待确认）**：如果两条路径确实并存，则项目最难的部分**不是设计更聪明的调度规则**
——那部分 Slurm 已经提供——**而是让不经过 Slurm 的负载变得可见**。
这也解释了为什么旧登记表会失败：它要求人手工报告一件系统本身看不见的事（INT-02/E07、INT-04/E19）。

> ⚠️ 本节的"两本账"是**推论**。访谈中没有直接询问"是否使用 Slurm"，也未核实是否存在允许直连的节点。
> 必须在管理员访谈中用一句话确认：**"组里的 GPU 是全部经由 Slurm 提交，还是允许 SSH 直连使用？"**
> 确认前，报告其余部分不得把它当事实使用。

**系统边界**：不实现 GPU 驱动或替代 Slurm 调度器，而是提供结构化申请、状态解释、策略配置、通知、审计
和原型化调度比较。系统应尽量读取 Slurm 和监控数据，避免要求用户重复维护一张独立表格。

## 4 单次访谈记录

### 4.1 INT-01：高频推理用户

**背景**。研二，在实验室一年多，几乎每天使用 GPU，主要进行模型推理优化，常见任务需要 4 张或 8 张卡。

**最近经历**。受访者计划使用一组 AMD GPU，但发现队列中已有十多个任务，预计需要等待十多个小时，最终放弃该资源。
过去通过在实验室口头询问判断资源，信息不够准确；部署 Slurm 后，可以通过命令查看队列，准确性明显改善。

**规则与公平**。受访者认为当前明确规则主要是任务必须通过 Slurm 提交。其个人会主动选择使用人数较少、
性能稍弱的资源，并把实验拆成较短任务以降低对他人的影响。对于固定 GPU 小时配额持反对态度，
理由是不同任务需求差异较大。

**异常证据**。早期曾有 Docker 容器被他人误停。由于没有收到通知，受访者先按机器故障排查，
约半天后才通过日志确认是人工停止。该经历直接支持任务所有权标识、人工操作通知和审计记录。

**需求线索**。希望看到前方任务预计剩余时间和自己的大致启动时间；建议队列考虑任务时长，
短任务可获得较高优先级；任务超过预计时长时应被识别。但"直接自动杀掉"只能视为受访者建议，
仍需管理员和安全性评审。

### 4.2 INT-02：高频用户与轻量权限协助者

**背景**。高年级学生，几乎每天运行推理任务，常用 8 卡；偶尔有人向其询问服务器权限，但其不是正式硬件管理员。

**现行流程**。在没有辅助工具时，较难从服务器进程准确判断任务所有者；使用 Slurm 后能够看到任务发起者。
实验室曾维护 GPU 资源使用列表，要求填写任务说明和预计时长，但成员逐渐不填写，且表格维护困难，最终停用。

**等待与任务差异**。典型等待约半小时到一小时，会打断工作节奏但通常不直接影响总进度。
调试任务被认为不适合中断，可重复的批处理任务相对适合让出资源。
受访者承认会为时长估计留出缓冲，说明申报值并不等于真实运行时长。

**公平与紧急任务**。受访者认为当前大体采用先到先得，但单个用户连续提交大量任务可能让服务器一整天都满载；
固定配额又可能压制计算量本来较大的任务。其接受毕业或截止任务优先，但强调应先说明任务和理由，
不能无解释地停止他人任务。

**需求线索**。希望系统对紧急任务提供受控优先处理，并显示大致完成时间；预计时长仍应由申请人填写，
系统可基于历史数据辅助，但不应假装能精确预测。

### 4.3 INT-03：较新成员与高频用户

**背景**。研一/较新成员，入组约一年，日常进行推理类任务，常用多卡资源。

**流程演化**。过去使用预约表时，出现用户占用时间段但没有实际使用 GPU、其他人又无法使用的情况；
切换到 Slurm 队列后，该问题得到缓解，受访者认为 GPU 利用率较高。当前提交任务通常不要求填写额外申请信息。

**现有调度认知**。受访者认为队列机制相对公平，并提到实验室已经设置短任务优先和等待保护：
时长较短的任务优先级较高，同时不能让任务无限等待。这说明原型 B 的部分规则在真实环境中已有雏形，
可以作为比较基线，而不是从零假设。

**异常与通知**。当队列或服务器出现问题时，可能需要管理员权限恢复。受访者明确希望服务器不可用时收到邮件通知。
其白天可接受等待约一小时，并希望知道前方还有多少任务。

**新成员视角**。遇到问题主要询问熟悉的同学，愿意使用面向新成员的规则说明和自助帮助。
对任务时长及等待规则，受访者认为需要由人参与确认，而不是完全由机器决定。

### 4.4 INT-04：短任务、自服务使用者

**背景**。高年级/博士生。最近一次任务是把 Transformer 中某个低层算子的实现替换为 CUDA 版本，
因此在动手前就明确知道需要 GPU。

**完整路径**。受访者的实际操作链是：**SSH（或 VSCode Remote，本质仍是 SSH）登录 → `nvidia-smi` 查看
显存与利用率 → 发现有卡空闲 → 按卡数与显存大小直接运行 bash 脚本**。整个过程**没有询问任何人、
没有登记、没有预估时长**，结束时也**不通知他人资源已释放**（INT-04/00:57–02:50、03:49–04:07）。

**选择依据**。"组里有不同类型的机器，我自然选择了我最熟悉的、英伟达 5090 的显卡"
（INT-04/02:05–02:15）——选择依据是**熟悉度**，而不是负载、规则或任务匹配。

**对现有登记机制的评价**。受访者确认组里此前做过用表格登记机器占用的工具，但表示：
"如果不是论文投稿或者其他什么要紧的项目之前，其实大家不会那么急，或者说队列也没有那么长，
所以其实没有经过与别人的沟通"（INT-04/03:24–03:47）。
更直接的判断是：**"去维护那个表格的时间，甚至比跑实验的时间都长。"**（INT-04/04:46–05:02）

**规范性的自我要求**。受访者主动提出，理论上跑实验前应先估算**卡时**与 **checkpoint 的存储占用量**，
"会不会把服务器挤爆"，并认为"无论实验类型是什么样，这其实应该是一个必须要做的过程"
（INT-04/04:07–04:32）。

**异常处理**。机器出现问题时，受访者的第一反应不是找管理员，而是"看一下进程是谁起的，可能就能找到对应的用户，
然后去跟他协调"；实在无法解决，才去找管理员——**而管理员是由高年级"大师兄"兼任的**（INT-04/05:34–05:52）。

**本场访谈的独特价值**：

1. 它提供的不是"再补一个同样的人"，而是一类**被现有流程完全漏掉的用户行为**；
2. 它给出了"登记成本 > 收益 → 规则失效"的**直接证词**，与 INT-02 的"登记表停用"形成多源印证；
3. 它修正了对 H1 的理解——短任务用户并不觉得状态不透明，`nvidia-smi` 对他们已经够用；
4. 它首次提供了**管理员角色性质的证据**（高年级兼任），这直接影响 S6 的定义与访谈方式。

**边界**。单场 6 分钟，只覆盖现状流程、协调与异常三块；**未涉及**紧急任务、公平偏好、隐私与规则接受度。
受访者实验类型单一（短任务、单/双卡），**不能代表长任务或多卡用户**；
"维护表格比跑实验还长"是**主观判断**，不是实测数据，引用时按观点处理。

## 5 跨访谈主题分析

### 5.1 主题一：状态透明的缺口已从"有没有队列"转向"队列意味着什么"

Slurm 已能展示任务和排队顺序，但访谈对象仍缺少对等待的**可行动解释**。INT-01 因预计等待十多个小时而放弃；
INT-02 和 INT-03 白天可接受的等待约一小时，超过后会暂停、换资源或转做其他工作。
系统应提供**区间估计和不确定性**，而不是给出无法保证的精确时间。

> **但这一主题有边界**：INT-04 在无争抢场景下认为 `nvidia-smi` 已足够，不觉得不透明。
> 因此本主题应表述为"**资源争抢期的解释缺口**"，而不是"普遍的状态不透明"。

### 5.2 主题二：低填写成本是系统采纳的前置条件

多段独立经历表明，纯手工表格不可靠：一类表格因无人持续填写而停用（INT-02/E07），
另一类预约表产生"占位但未使用"（INT-03/E11），INT-04 更直接地判断"维护表格比跑实验还久"（E19）。
因此，任务状态、实际开始时间、结束时间和资源占用应优先从 Slurm 或监控自动同步；
用户只补充系统无法获得的少量信息，如任务目的类别、截止时间、可中断性和联系人。

> **强化**：v1.0 把这条当作"采纳条件"，v2.0 依据 INT-04 将其提升为**设计约束**——
> 原型 A 若仍以"用户填报"为前提，几乎必然重演旧表格的结局。

### 5.3 主题三：公平不是平均分，而是可说明的情境化规则

受访者并不支持简单平均配额，也不完全满意纯先到先得。现有偏好包括：短任务适度优先、等待时间增长后提升优先级、
真正紧急任务可优先、不同任务规模应区别处理。这些规则存在相互冲突，需要在原型中通过具体场景验证，
而不能直接汇总为一个不透明的总分。

### 5.4 主题四：自动化必须识别任务可中断性

调试和关键验证任务被认为不宜中断，可重复计算任务更适合让出资源。若系统只根据超时直接终止任务，
可能造成难以恢复的实验损失。更稳妥的流程是"提醒—宽限期—用户确认—必要时管理员处理"，并记录中断原因和操作者。

### 5.5 主题五：人际协调有效，但不可作为唯一治理机制

当前冲突通常由使用者私下协商，受访者也普遍愿意为真正紧急的任务让步。这种机制在小规模团队中成本较低，
但依赖熟人关系和个人道德，无法保证一致性、可追踪性或对新成员的公平。
INT-04 描述的"先 `ps` 找进程属主再私下协调"正是这一机制的典型形态（E21），且**整个过程不留任何记录**。
系统应保留沟通空间，同时提供最小规则、理由和记录。

### 5.6 主题六（新增）：痛点具有**时段性**，不是常态

INT-04 指出，只有在论文投稿或要紧项目之前"大家才会那么急"；平时队列不长，因此不值得付出协调成本。
若属实，则：

- 系统的价值集中在**资源争抢期**，平时应尽量"无感"，不能要求持续维护；
- 评估方案必须包含**两种负载场景**（宽松期 / 争抢期），否则测不出差别；
- 这本身是一个需求权衡：为争抢期设计的机制，会在宽松期成为额外负担。

### 5.7 主题七（新增）：可见性缺口可能源自分叉的使用路径

前 3 场描述的 Slurm 路径与 INT-04 描述的直连路径，**在可观测性上是两个世界**。
若两条路径并存，则任何只读取 Slurm 的方案都只能看到一部分真实负载；
而任何要求直连用户主动登记的设计，都会撞上主题二所述的成本约束。
**这是本项目最深的一处需求张力**，但目前仅为推论（见 §3）。

## 8 对两个原型方案的影响

### 8.1 原型 A：轻量申请与透明先到先得

原型 A 仍可作为基线，但**不应简单复刻曾经失败的共享表格**。建议将其定义为"Slurm 自动同步 + 极少字段 + 明确队列顺序"：

- 自动读取资源与任务状态，用户只补充预计时长、可中断性和匿名联系方式；
- 以提交时间为主排序，展示前方任务和大致等待区间；
- 对任务超时、服务器离线和人工操作发送通知；
- 管理员调整时必须填写理由，但不计算复杂综合分数。

该方案主要验证：**低填写成本是否能够避免旧表格失效**；透明的先到先得加等待信息是否已足够满足多数场景。

> **INT-04 带来的修订**：原型 A 的**第一设计假设不是"先到先得公平"，而是"零填写也必须可用"**。
> 否则它会在真实实验室里重演"表格没人填"的结局（CAND-14）。

### 8.2 原型 B：可解释的动态优先级与候补

访谈不支持把"每人固定平均配额"作为原型 B 的核心。更符合证据的初始因素是：

1. 等待时间及老化机制，防止任务无限等待；
2. 预计任务时长，对短任务适度倾斜但避免长任务饥饿；
3. 已说明理由的截止/紧急程度；
4. 资源匹配与任务可中断性。

配额可作为软约束或异常提醒，而不是简单的平均硬上限。排序结果必须展示主要原因；
任何抢占或自动终止都应经过提醒、宽限和确认。

### 8.3 原型差异维度的修订建议（由竞品分析引出）

v1.0 把两个原型的主要差异放在"**先到先得 vs 配额/优先级**"。竞品分析表明，
后者的大部分能力 Slurm 已经内置，若原型 B 只是重写一遍，**区分度和说服力都会下降**。
建议把差异维度改为**系统边界与自动化程度**：

| 比较维度 | 原型 A | 原型 B |
|---|---|---|
| 核心机制 | 申请时间为主，规则简单 | 等待老化、时长、紧急性、资源匹配综合 |
| **系统边界** | **薄层**：调度完全交给 Slurm | **厚层**：自带配额与排序评估，Slurm 只负责执行 |
| **非 Slurm 使用** | 不处理（假设全部走 Slurm） | 通过监控与心跳推断占用，尽量覆盖 |
| 数据录入 | 最小字段，自动同步 | 需额外填写紧急理由、可中断性等 |
| 解释方式 | 展示顺序与人工调整理由 | 展示影响排序的主要因素和变化原因 |
| 关键风险 | 长任务或批量提交占据队列；直连用户不可见 | 规则复杂、可被策略性填写、维护成本高 |
| 访谈验证重点 | 是否足够透明、是否愿意持续填写 | 是否理解排序、是否接受紧急与短任务倾斜 |

> 该修订**不推翻建议书**，而是让差异更可观察、更符合真实设计空间。
> **是否采纳取决于管理员对"是否存在直连使用"的回答**（§9.3 第一问）。

## 11 生成式 AI 使用与人工核验说明

本报告使用本地语音识别模型（Whisper large-v3-turbo）对四段真实录音生成初步转写，并使用生成式 AI 辅助
归类、形成表格和排版。人工核验措施包括：

- 逐段检查时间戳；
- 结合访谈问题和领域术语校正明显近音错误（如"显存占用""队列""checkpoint"）；
- 不把无法识别的型号、姓名或短句写入结论；
- 所有需求均保留录音来源；
- 将**推论、受访者观点和已发生事实**分开表述。

**已知局限**：自动转写对中英文混合术语、GPU 型号和低音量短答的识别不稳定。INT-04 的原始转写中
存在多处明显误识别（如"内情尊重情况""队力""硅子"），已按上下文校正为"显存占用""队列""规则"，
**未增补受访者未说的内容**；原始输出保留在 `转写/INT-04.txt` 备查。

**本报告没有生成虚构访谈、没有补造管理员意见，也没有把模拟数据描述为真实数据。**
正式纳入需求基线前，应由项目组再次抽听关键片段，并将匿名摘要发给受访者确认。
