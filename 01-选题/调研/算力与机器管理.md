# 调研：课题组「算力与机器管理」

> 来源：AI 调研 agent 产出（2026-10-14）。**尚未人工核实全部链接**，引用进报告前须逐条验证。
> 用途：访谈弹药 + 切片选型。

**场景定位**：10–30 人课题组、多台自建 GPU 服务器。现实分两条路线——
有调度器（Slurm/LSF）路线，和**裸机路线**（纯 `nvidia-smi` + 人肉约定）。
课题组的现实多落在后者，而最佳实践几乎都从前者抄。

| 事项 | 最佳实践 | 现成工具 | 是否值得自研 | 干系人与潜在冲突 |
|---|---|---|---|---|
| **占用登记（谁在用哪张卡）** | 不做"登记表"，让**真实占用状态成为唯一真相源**：从驱动层读进程→用户映射，实时展示，登记是"副产品" | 单机 `nvitop` / `gpustat` / `nvtop`；多机网页 `gpustat-web`；有 Slurm 则 `squeue`/`sinfo` | 技术层不值得自研；**"跨机聚合 + 组内可见入口"值得自研**（网页或群机器人，cron 轮询即可） | 用卡学生（讨厌被要求登记）× 管理员/导师（要可追溯）。**冲突：强制登记 vs 靠自觉**——登记拦不住人偷用 `CUDA_VISIBLE_DEVICES`，能直接读驱动就不该靠人填表 |
| **占用释放（手动侧）** | 约定式：跑完就 `exit`/`scancel`/`docker stop`（Stony Brook、Purdue、北大均有明文要求） | Slurm `scancel`；裸机就是 `release`/`free` 小脚本 + 群公告 | 低（就是个封装命令） | **手动释放依赖自觉 = 公地悲剧**，靠工具解决不了，需规则 + 可见性 |
| **占用释放（自动侧）** | 业界主流**"空闲即回收"**：GPU 利用率低于阈值持续 N 分钟 → 警告 → 终止。Univ. of Florida 有正式《Idle GPU Policy》：0% 持续 1 小时即杀；多卡任务一卡空闲即整 job 杀；禁止"空跑假负载保卡" | Slurm `Epilog` + wall-time/QOS；裸机 cron + `nvidia-smi --query-compute-apps` 或 DCGM 指标判断空闲 → kill；MPS/MIG 切片 | **值得自研**（阈值高度本地化，无通用产品），但**必须"先通知后释放"多级策略** | **最核心冲突：自动释放 vs 误杀正在跑的任务**——评测/预处理/CPU 瓶颈阶段 GPU 利用率天然低，误杀代价可能是几天训练。缓解：宽限期、告警、长任务豁免标记、只在"持进程但 0 利用率"时判定 |
| **机器台账 / 资产清单** | 当小型 CMDB 做：型号、序列号、位置、采购年份、保修、显卡、负责人、IP/MAC、变更历史。允许**机器自述**（定期采集回填），避免人工维护腐化 | `NetBox`（DCIM 事实标准）、`GLPI`、`RackTables`；轻量可用 Git 里的 YAML/Markdown + CI 渲染；采集 `dmidecode`/`nvidia-smi -q`/`lshw` | 不建议自研整套 CMDB；**值得自研"采集脚本 + 与台账 diff 报警"** | 管理员（要准）、导师/采购（算钱折旧）、使用者（找可用机器）。**冲突：数据录入成本 vs 数据新鲜度** |
| **环境约定（可复现）** | HPC 答案：**模块/容器二选一**。软件栈用 Lmod 分层；依赖用容器锁定（HPC 免 root 用 Apptainer）；环境要"可打包可搬运" | `conda`/`mamba`+`conda-lock`；`conda-pack` 打包可搬迁环境；`Spack`；私有镜像仓 `Harbor`；`uv`/`pixi` | 不自研环境管理器；**值得自研"组内基线 + 命名规范 + 公共镜像 + README 约定"**，配 CI 校验 | 新人（想一键跑通）× 老手（有自己手搓环境）× 管理员（要能复现排障）。**冲突：统一规范 vs 个人自由度；可复现成本 vs 赶论文速度**——典型质量属性谈判 |
| **共享存储（数据/模型复用）** | ①单一共享文件系统（NFS → Lustre/BeeGFS/Ceph），路径统一 ②模型/数据集缓存**集中预热**，禁止各自重复下载 ③内容寻址缓存天然去重 | NFS/Lustre/BeeGFS/Ceph；HF 缓存统一 `HF_HOME`（NFS 上禁用软链接缓存）；`huggingface-cli download` 预热；国内 `ModelScope`；`DVC` 版本化 | 不自研存储系统；**值得自研"配额/清理策略 + 重复下载可见性"** | 全体用户 × 管理员（磁盘谁占满）。**冲突：留着以防万一 vs 配额清理；公共缓存写入权限 vs 误删**；常与"数据算不算组资产、毕业留不留"纠缠 |
| **故障报修** | 最佳实践是**监控自动发现并主动告警**，而非等人报修：Xid 错误、ECC、掉卡、温度、磁盘满、掉线自动触发 | `Prometheus`+`Alertmanager`+`Grafana`+DCGM exporter；轻量 `Uptime Kuma`；工单用飞书/企微机器人、Issues、`Zammad`/`RT` | **值得自研一个薄层**（群机器人 + 工单表单 + 状态看板）；监控与工单用现成 | 使用者（报修无人响应）× 管理员（信息不全、被私聊轰炸）。**冲突：随手群里喊 vs 走工单留痕**——强制走工单会让报修率下降 |
| **资源公平性** | 成熟解法是**配额 + 计费权重 + 优先级衰减**，不是道德劝说：按 TRES 计费、每人/项目上限、历史用量加权 | Slurm Fair Tree 公平份额、QOS、`TRESBillingWeight`、`GrpTRES`；K8s 用 `Kueue`/`Volcano`；整卡切分用 MPS/MIG；实验平台 `Determined AI`、`SkyPilot` | **公平策略层（裸机场景）值得自研**（如每卡每日软配额 + 超限申请）；**不要自研调度器** | 大模型组（要长时独占）× 小任务用户 × 导师。**最典型冲突：公平 vs 效率**；"按卡数"vs"按显存/算力"的公平定义本身就会被争 |
| *（增补）卡的分时共享* | MPS 做 SM/内存分区，MIG 做硬件级隔离 | MPS / MIG；Slurm GRES | 不值得自研（驱动能力） | 共享者 × 独占者。**冲突：隔离性/可预测性 vs 利用率**；MIG 需 Ampere 及更新的卡 |
| *（增补）交互式环境即服务* | 给不熟命令行的人提供网页版 Jupyter/VSCode，自带**会话超时回收** | `Open OnDemand`、`JupyterHub` | 部署重，一般不自研 | 新手 × 管理员。**冲突：便利性 vs 资源泄漏**（浏览器不关 = 卡一直占） |

## 最适合作课程项目的切入点

**A（首选）占用登记 + 释放的工作流与规则。**
干系人边界清晰（用卡学生/管理员/导师，10–30 人可全量访谈），目标冲突密集且真实——
**强制登记 vs 靠自觉**、**自动释放 vs 误杀长任务**、**公平 vs 效率**。
正好练 goal model、冲突分析、非功能需求（误杀率、回收时延、可追溯性）与验收标准。
它天然是**社会技术系统**问题，不是纯技术题。

**B（次选）环境约定与共享存储的"组内可复现"。**
驱动它的是质量属性（可复现性、可维护性、新人上手时间），
冲突是**统一规范 vs 个人自由度**、**留数据的成本 vs 配额**，容易写出可度量的非功能需求，
但访谈材料不如 A 有戏剧性。

### 关于"真实日志数据"能否作为需求获取证据

**能，但要限定条件。** 对既有系统的**文档分析/行为观测（含日志）是公认的 elicitation 技术**，
近年还有 "data-driven requirements engineering" 一说。日志（Slurm `sacct`/`sreport`、
Prometheus+DCGM 或 `nvidia-smi` 轮询序列、HF 缓存访问）能提供：

1. **定量基线**——真实利用率、空闲时长分布、高峰时段、人均占用，把"卡不够用"从吐槽变成数字
2. **与访谈三角验证**——暴露 user-stated 与 actual 的差距
3. **边界条件与异常路径**

**三条硬限制**：

- 日志只描述"发生了什么"，**不等于"应该怎样"**（rationale 仍须访谈补足）
- 受**隐私与合规约束**（user-level 数据需组内授权，聚合匿名化后再用）
- 受**记录字段限制**（"为什么这人宁可空占也不释放"这类，日志永远看不到）

→ 正确用法是**把日志当证据之一而非唯一来源**，并在报告里写明数据获取的伦理边界。
