# 调研：组内知识管理 + 新人入门 + 对外门户

> 来源：AI 调研 agent 产出（2026-10-14）。来源清单在文末，**引用进报告前须逐条核实**。
> 用途：访谈弹药 + 切片选型。

| 事项 | 最佳实践 | 现成工具 | 是否值得自研 | 干系人与冲突 |
|---|---|---|---|---|
| **1. 主页内容架构** | 一个主页同时服务"同行/招生对象/公众"通常都做不好，应**按受众分流**。每 6 个月至少更新一次，**联系方式失效最伤招生**。"Join the lab" 页最重要，应写清：当前方向（不是几年前的）、头一两年典型项目、需要什么背景、资助情况、现有学生各自在做什么、申请时间线。学生本人视角的内容最有效 | al-folio（Jekyll）、Hugo Blox research-group starter、greenelab lab-website-template（Manubot）；托管 GitHub Pages / Netlify / 校内服务器 | 不建议从零写站点框架；值得自研的只是**内容结构与数据管线**（见 2、3 行）。组站烂尾根因是"内容更新靠人肉" | PI（展示、招生）× 学生（个人主页自主、隐私）× 校友（时效）× 学院（品牌合规）。**冲突：统一规范 vs 个人习惯；公开透明 vs 未发表工作保密** |
| **2. 论文列表数据来源与自动同步** | 不要手编 BibTeX，用稳定标识（DOI/ORCID/arXiv ID/DBLP PID）自动抓。**多源交叉**（DBLP + Crossref + Semantic Scholar + arXiv，有 key 加 OpenAlex）去重合并——单源会因限流"静默收窄"。⚠️ **Google Scholar 无官方 API，抓取违反 ToS，避开** | DBLP API（免费无 key）、Crossref REST（免费）、OpenAlex（免费、CC0）、Semantic Scholar API（需 key，限流严）、arXiv API（礼貌间隔 ≥3s）、ORCID Public API | **中等值得**：抓取—去重—合并—**人工审核**—落库这条管线可自研；底层 API 客户端不要自造 | **冲突：自动化 vs 准确性**（DBLP 滞后、预印本≠正式发表、作者重名）→ 必须有审核环节；及时性 vs 维护成本 |
| **3. 论文列表站点渲染** | 用 BibTeX 或抓取结果驱动渲染；按年/类型分组、作者高亮、BibTeX 一键复制 | Jekyll-scholar（al-folio 内置）、Hugo Academic CLI 导入 `.bib`、Manubot | 低，优先现成插件 | 展示美观 vs 元数据完整；组主页与 DBLP 不一致时以谁为准 |
| **4. 组内 Wiki 平台选型** | Wiki 作为组的 "cyberspace library"：仪器 SOP、环境搭建、协议、会议纪要、行政流程、onboarding；**模板 + namespace** 保证一致可检索；主页当目录 | DokuWiki（文件型、易备份）、Confluence、MediaWiki、Notion、Obsidian、GitBook/MkDocs/语雀/飞书 | 不建议自研 Wiki 引擎；值得自研的是"**模板 + namespace + 权限 + Git 集成**" | 平台统一 vs 各人已用工具（迁移成本）；云端便利 vs 数据自主/内网合规；开放编辑 vs 内容可信 |
| **5. Wiki 防烂尾治理** | **每页具名 owner + 复核周期**，否则必烂；把记录嵌入日常工作流（事情闭环即算完成）；归档 90 天未访问页；轮值"知识管家"+ **信息健康度指标**（检索无结果率、新人首次有效产出时间） | docs-as-code（仓库 + PR + CI 链接/过期检查）、Confluence label/review、任何 wiki 的 stale 标记 | **值得**。"页面 owner + 过期提醒 + 健康度看板"非常适合课程项目（边界清晰、干系人明确、可验收） | **记录成本 vs 科研产出压力**（不产出=不考核，记录被无限延后）；透明度/署名 vs 个人意愿；制度约束 vs 学术自治 |
| **6. 新生 onboarding** | 手册涵盖 ethos / how we work / 协议三类，不必单一文档。onboarding package 应含：门禁账号、邮箱群、联系人（紧急/行政/设施）、设备设施、工位、必读文献、**商定的时间线与里程碑**。手册**一学期内协作完成**而非多次短会。用"新人专属周会"或 buddy/老生带教（老生带教要**限流**以免压垮）。首个任务选独立"黑盒"或小评估任务，不放进关键路径 | Quarto + Zenodo Lab Group Handbook 模板（CC-BY-4.0）、Protocols.io 手册模板、WIN(Oxford) 模板、Holmes Lab / Ando Lab manual | **值得**。内容组特有，模板现成；自研点是"**分角色 checklist + 进度可见 + 可复用**" | 老生被重复提问 vs 老生科研时间；手册写得细 vs 像 micromanagement；统一流程 vs 因人而异；**一次性文档 vs 持续维护** |
| **7. FAQ 沉淀** | 把高频问题转成 Q&A 对，让新人"问"而不是"翻文件夹"；**从 20–30 条高频开始**；Q&A 与 SOP 冲突以现行 SOP 为准；组会每周分享一个问答；把知识贡献纳入组内评价 | Wiki 的 Q&A 页 + 站内检索；Confluence/Notion 数据库视图；检索增强问答（**AI 生成内容须可追溯、可复核，不可当权威**） | **值得（课程项目友好）**："从组会/聊天记录里挖 FAQ + 定期复核"是范围可控的自研点 | **透明 vs 隐私**（聊天内容、学生的具体困难）；**即时回答 vs 长期沉淀**（直接问老生最快、沉淀最慢却最有价值 → 导致没人沉淀） |
| **8. 必读文献与分享归档** | 分方向维护 recommended reading（入门→进阶）；组会/文献分享的 PPT 与笔记归档复用 | Wiki 页 + Zotero 群组库；Mendeley；共享盘 | 低—中，Zotero 群组库基本够用 | 个人文献习惯 vs 组统一库；版权/全文分发限制 |
| **9. 组内方向/项目全景图** | 让新人知道"组里在做什么"：方向—人—代表论文—在研项目的映射 | 主页方向页 + 内部 wiki 项目页 + 简单可视化 | 值得，但**"全景图半衰期短"**，自研重点应是"**变更触发更新**"而非图表美观 | 展示在研方向 vs 未发表保密/竞争；PI 战略叙事 vs 学生实际在做的事；**受益者与维护者不是同一批人** |
| **10. 招生页与开放日** | 按申请者类型（博士/硕士/本科/博后）分节，写清资格、期望、如何联系；PI 的指导理念/价值观声明能过滤不合适申请者 | 主页静态页 + 复用站点框架 | 低（本质是内容工作）；自研点：从内部信息自动生成招生页以减少重复邮件 | 招到更多人 vs 招到更合适的人；透明（资助/去向） vs 学校统一口径/隐私 |
| **11. 权限、隐私与数据治理（横切）** | **三级权限**：公开（门户）/ 组内（常规 wiki）/ 私密（会议材料、申报书、未发表数据）；编辑权限限于已确认 owner | 平台 ACL + 校内 SSO；内网/VPN；ELN（Confluence 可充当） | 低，优先用平台能力 | 开放透明 vs 隐私保密；便利 vs 安全合规；**个人数据自主 vs 组资产归属**（毕业后数据/笔记归谁） |

## 最适合作课程项目的切入点

1. **论文列表自动同步 + 门户/招生页生成（第 1、2、3、10 行）**。数据源（DBLP/Crossref/OpenAlex/ORCID/arXiv）全部有公开文档、可实测，需求边界清晰；天然产生可测的**非功能需求**（去重准确率、抓取时效、对限流的健壮性、审核时延）；干系人冲突真实可访谈（组统一列表 vs 个人主页自主、自动化 vs 人工审核、透明 vs 未发表保密）。不需要自建底层平台。
2. **新生 onboarding + FAQ 知识沉淀（第 6、7 行，配第 5 行治理）**。现状痛点明确（老生被重复提问、文档烂尾），**干系人最多**（新生、老生、导师、毕业校友），冲突最丰富（记录成本 vs 产出压力、透明 vs 隐私、制度约束 vs 学术自治）；非常适合访谈 + 用例/用户故事 + 卡片分类做 elicitation，且"**防烂尾"本身就是必须写进需求的质量属性**。

两者都落在"**用现成 API/模板、自研只做管线与约定**"这一层，范围可控、可交付、可验收。
