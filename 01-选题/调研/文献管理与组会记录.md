# 调研：组内文献管理 + 组会记录

> 来源：AI 调研 agent 产出（2026-10-14）。**链接未逐条人工核实**，引用进报告前须验证。
> 用途：访谈弹药 + 切片选型。

## 一、文献与知识

| 事项 | 最佳实践 | 现成工具 | 是否值得自研 | 干系人与冲突 |
|---|---|---|---|---|
| **组织维度（按项目/方向，而非大杂烩）** | 主流是**一个项目/综述建一个 group**（"两篇综述＝两个 group"），而非一个超大库；用 collection + tag 做二级视图，放一个"readme 便签"说明本库怎么组织 | Zotero group library、Paperpile shared library | **组织模型值得自研**（"视图/规范"层）；管理内核不值得 | PI、高年级（已有自己习惯的私有库）、新生（要按项目找）。**冲突：按人组织 vs 按项目组织**；历史库迁移成本；"谁有权重构目录" |
| **组内共享文献库** | 先存个人库 → 清元数据 → 再拷进 group；**notes/annotations 要放 group 库而非个人库**（个人笔记不会随拷贝过去）；动前先 sync | Zotero group（Private / Public-Closed / Public-Open；**存储配额记在 group owner 名下**）、Paperpile（Viewer/Editor/Admin；live copy vs independent copy） | 不值得；值得自研的是"入库 SOP + 命名规范"文档/检查脚本 | 组内成员、已毕业成员（账号/所有权）、外部合作者。**冲突：共享 vs 私有笔记**（师兄不愿公开半成品思路）；订阅 PDF 版权限制 |
| **某方向探索者的 follow 流**（如做 RL 的师兄） | "标签 + 推荐/向量检索"式个人订阅；个人 tag 对应自己的方向，而非全组方向 | arxiv-sanity-lite | 值得自研的只有"个人 ↔ 组库"的同步/发布环节 | 探索者、PI（关心方向是否偏离）。**冲突：个人方向自由 vs 组项目对齐**；个人订阅噪音是否进公共库 |
| **arXiv / 顶会 每日推荐** | 订阅源 + LLM/热度过滤 + IM 推送；强调"是采样器不是综述" | Zotero 自带 Feed 阅读器、arXiv 官方 RSS、HF Daily Papers、Semantic Scholar API、Connected Papers、alphaXiv、Paper Digest、papers.cool、scholar-inbox | **推荐自研**：薄胶水层（多源聚合 + 去重 + 按方向分频道 + 推 IM），成本低、需求清楚 | 全组、PI、新生。**冲突：推荐算法偏好 vs PI 判断**；推送骚扰 vs 漏读 |
| **精读笔记沉淀** | 笔记与文献**双向链接**（笔记挂在条目上，而非散在个人目录）；区分"摘要/我的想法/待验证" | Zotero notes+annotations、Obsidian、语雀、Notion | 自研"模板 + 挂载规范"；不值自研编辑器 | 写笔记的人、后来读的人、PI。**冲突：共享 vs 私有**；写完没人看的激励问题 |
| **领域脉络 / 综述继承** | "reading path"式入门清单 + 已有综述作锚点；新人先读组内指定 3–5 篇 + 1 篇综述 | Connected Papers、Semantic Scholar、wiki | **推荐自研**：把"前辈精读笔记 → 新生入门路径"做成显式资产 | 新生、师兄、PI。**冲突：整理者收益低 vs 受益者收益高（搭便车）** |
| **投稿 SOP：引用格式统一** | 统一 `.bib` 单一真源 + 稳定 citation key（避免改库导致 LaTeX 引用断掉） | Better BibTeX for Zotero、Zotero CSL、Overleaf | 不值得；值得自研的只是"组内投稿 checklist" | 投稿作者、PI。冲突：个人习惯 vs 组规范 |
| **投稿前引用核查** | 提交前扫 DOI 是否被撤稿 / 是否引错版本 | Retraction Scanner、Zotero 内置撤稿检测、Semantic Scholar API | 不值得自研 | 作者、PI（声誉风险）。冲突：核查耗时 vs 收益 |
| **写作模板与协作** | 组级 LaTeX/Markdown 模板（会议模板 + 公共 preamble/bib/图规范） | Overleaf 模板库、组内 Git | 不值得 | 作者、合作者。冲突：模板版本混乱 |

## 二、组会

| 事项 | 最佳实践 | 现成工具 | 是否值得自研 | 干系人与冲突 |
|---|---|---|---|---|
| **会议语音转写** | 会前告知 + 转写 + 说话人分离 + 时间戳；中文会议需专门评估中文/中英混合准确率 | Whisper、WhisperX（词级时间戳+pyannote 说话人分离）、faster-whisper、pyannote-audio；飞书妙记、通义听悟 | **强烈不建议自研 ASR 内核**；值得自研的是"转写之后的编排" | 全组、PI、被录音者。**冲突：录音隐私**；境外服务 vs 境内数据合规；准确率不达标谁背锅 |
| **自动摘要** | 分层摘要：全文摘要 + 章节速览 + 发言总结 + 待办 | 通义听悟 API（含自定义 prompt）、飞书妙记 API、Otter.ai、Fireflies.ai、tl;dv、Granola、Notion AI Meeting Notes | **建议自研**：用固定"组会模板"约束输出（避免自由发挥失真），做"AI 摘要 + 人工确认"两段式 | PI（权威性）、汇报人（被记错）、全组。**冲突：自动摘要失真 vs 可信性**；"PI 说的"被改写成不同口径；技术术语/代码名转写错误 |
| **待办 / action item 提取与追踪** | WHO + WHAT + WHEN；"ASAP 不是 deadline"；**下次会开头先 review 上次 action items**；纪要 24h 内发出 | 妙记 todos、听悟待办、Fireflies、tl;dv、Notion/Linear/Jira | **最值得自研**：提取 → 确认 → 分配到人 → 跨会追踪 → 与项目关联，这条闭环**没有现成工具完全贴合课题组** | 汇报人、被指派者、PI、秘书。**冲突：跟踪 = 绩效监控**的抵触；口语指令 vs 书面指令不一致 |
| **纪要结构化模板** | 议题 + 讨论要点 + **DECISIONS** + **Action Items 表(#/事项/owner/截止/状态)** + 下次会议；记录人轮值；纪要存 wiki 而非散落群文件 | 组内 wiki、BRIDGE Lab 公开组会结构、Research-Log LaTeX 模板 | **推荐自研**：模板 + 归档结构 + 与文献库弱关联 | 记录人（轮值）、PI、缺席者、新生。**冲突：纪要算不算"组内公开"**；记录人权力（决定什么被记为决定）；轮值负担 |
| **工具选型：本地 vs 云 vs 境内服务** | 涉及未发表 idea 与外部合作内容时优先可控存储；跨境传输单独评估 | 境内：妙记/听悟；境外：Otter/Fireflies/tl;dv/Granola；自建：WhisperX + 本地 GPU | 自建仅在"有敏感内容且愿维护"时值得，否则买入 | 组内、院系信息化、合作方。冲突：便利 vs 合规；学校统一采购 vs 组内自选 |
| **隐私与知情同意（本课程关键）** | 录音前**明确告知**：谁录、为何录、是否转写/生成 AI 摘要/交第三方、谁能看、存多久、如何撤回；**开场再次确认**；有人拒绝时提供"不录音的替代方案"；音频与视频分别单独同意 | 依据《个人信息保护法》（2021-11-01 施行）第 13/14/17 条（同意、充分知情自愿、显著方式告知）；《民法典》第 1032/1033 条（隐私权、禁止窃听） | **必须自研**：知情同意流程 + 撤回机制 + 留存期策略 + 访问控制——**这本身就是"需求"而不是"功能"** | PI、全组、学校伦理/合规、外部参会者。**冲突：权力不对等（学生能否真拒绝）**；平台录制提示不能替代逐人知情同意；境外服务的数据出境 |
| **数据留存 / 访问控制 / 撤回** | 转录后尽快转写并去标识化，原始录音仅在必要时保留；到期销毁；加密存储；"中途加入者"要重新说明 | 各组自建策略 | **必须自研**（策略 + 工具辅助） | 组内、学校合规、已毕业成员。**冲突：留存越长越好用 vs 越长越危险**；撤回后已生成的摘要怎么办 |

## 最适合作课程项目的切入点

1. **主线建议：组会"转写 → 结构化纪要 → action item 闭环"**。同时具备四要素：
   真实且已明确的需求（需求方点名要"语音会议自动记录"）、清晰系统边界
   （**转写引擎买现成，自研只做编排层**）、丰富的干系人冲突、以及一个必须写进文档的**伦理风险**（录音与知情同意）。
   需求方说"能跟别的扯上关系即可"，正好对应"弱耦合接口"这一课。
2. **次线：文献的"按项目/方向组织"层**。注意——**不要做文献管理器，要做组织模型与视图**
   （按项目 collection + 方向 tag + 双向链接笔记 + 入门路径），固化成组内规范与轻量胶水。
   Zotero group / Paperpile 已是成熟底座，自研价值全在"怎么组织、谁维护、如何继承"。
3. **两块的最优组合**：以组会为主线，把纪要里的 action item / 参考文献作为"弱关联"接回项目文献视图
   ——这给出一张漂亮的系统上下文图和两个子系统边界，是 RE 文档里最容易出彩的部分。
4. **强烈不建议自研（写进"方案权衡"章节）**：ASR 内核、文献管理内核、引用样式。
   把这几项列为"采购/复用"，让"自研 vs 采购"的论证变成实实在在的需求工程练习。
5. **最值得自研、也最能体现 RE 价值的**：action item 的"提取—确认—指派—跨会追踪"闭环，
   以及知情同意/撤回/留存策略。前者有功能需求 + 可验证验收标准，后者是典型非功能需求（隐私、可信、可追溯）+ 伦理约束。
6. **冲突素材最富的两点（可作访谈主问题）**：
   ① "**按人组织 vs 按项目组织**"（同一份文献，师兄按方向归档、新生按项目找）；
   ② "**共享 vs 私有 + 录音**"（师兄不愿公开半成品精读笔记；有人不愿被录，而权力不对等使"拒绝"难以开口）。
7. **可直接复用的现实约束（写进假设与依赖）**：Zotero 群组库存储配额记在 group owner 名下；
   境内服务便于合规但转写质量需实测；境外工具技术更成熟但触及数据出境；**无任何平台能保证"不被他人录制"**。

**一句话结论**：以**组会纪要 + action item 闭环**为自研核心、以**按项目组织的文献视图**做弱关联扩展、
把 **ASR 与文献管理内核整体买现成**——这是需求清晰度、干系人冲突密度、伦理风险显性度三方面都最划算的选题。
